# Lambda: Generate Code

Orchestrates AI-powered code generation from Jira user stories or GitHub issues using Claude via Bedrock. Handles multiple trigger sources, creates execution plans, and generates code asynchronously via SQS.

## Purpose

The generate-code Lambda function integrates with Jira and GitHub to automatically generate code from approved stories/issues. It:

- **Receives triggers** from Jira Automation (via SSM) or GitHub webhooks
- **Creates git branches** for generated code
- **Sends async messages** to SQS for plan generation (avoids timeout issues)
- **Generates execution plans** using Claude via Bedrock + knowledge base context
- **Executes steps** to generate files, commit changes, and create pull requests

## Architecture

The Lambda uses a multi-path architecture supporting both Jira and GitHub triggers:

```
Path 1: Jira Automation (SSM Document)
  └─> Jira Automation rule fires
  └─> Assumes cross-account IAM role
  └─> Invokes SSM Automation Document
  └─> SSM invokes Lambda directly with Jira payload
  └─> Create git branch
  └─> Send "generate_plan" message to SQS

Path 2: GitHub Webhook (API Gateway)
  └─> Verify signature
  └─> Parse webhook payload
  └─> Create git branch
  └─> Send "generate_plan" message to SQS
  └─> Return 200 OK (<10 seconds)

Path 3: SQS Message Processing (shared by both triggers)
  ├─> Action: "generate_plan"
  │   └─> Query knowledge base for context
  │   └─> Generate execution plan with Claude
  │   └─> Commit plan to branch
  │   └─> Send "execute_step" message for step 1
  │
  └─> Action: "execute_step"
      └─> Get plan from branch
      └─> Query knowledge base for step context
      └─> Generate code with Claude
      └─> Commit files to branch
      └─> Send message for next step OR create PR
```

## Triggers

### Jira Automation (via SSM)

**Flow:** Jira Issue → Jira Automation Rule → AWS (assume role) → SSM Document → Lambda

**Jira Smart Values Mapping:**
| SSM Parameter | Jira Smart Value | Description |
|---------------|------------------|-------------|
| `issueKey` | `{{issue.key}}` | Jira issue key (e.g., PROJ-123) |
| `issueSummary` | `{{issue.summary}}` | Issue title |
| `issueDescription` | `{{issue.description}}` | Full user story/description |
| `componentKey` | `{{issue.components.name}}` | Maps to GitHub repo path (e.g., owner/repo) |

**Setup Requirements:**
1. Enable `enable_jira_integration = true` in Terraform
2. Deploy to get the `atlassian_automation_role_arn` output
3. In Jira Automation, create AWS connector with the role ARN
4. Copy the External ID generated by Atlassian
5. Add `jira_external_id = "the-external-id"` to tfvars and re-deploy
6. Create Jira Automation rule that invokes the SSM document

**Jira Payload (via SSM):**
```json
{
  "source": "jira",
  "issueKey": "PROJ-123",
  "issueSummary": "Add list-recent-docs handler",
  "issueDescription": "As a user, I want to...",
  "componentKey": "owner/repo"
}
```

### GitHub Webhook

**Event:** Issue labeled with `approved-for-generation` or `approved-for-plan`

**Supported Labels:**
| Label | Behavior |
|-------|----------|
| `approved-for-generation` | Full code generation - creates plan, generates code, creates PR |
| `approved-for-plan` | Plan-only mode - creates plan and PR without generating code (~$0.01-0.02 vs ~$1-5) |

**Endpoint:** `POST /github/webhook/generate-code`

**Required Headers:**
- `x-hub-signature-256`: HMAC signature for verification

**Webhook Payload:**
```json
{
  "action": "labeled",
  "label": {
    "name": "approved-for-generation"
  },
  "issue": {
    "number": 123,
    "title": "Add list-recent-docs handler",
    "body": "User story and requirements...",
    "html_url": "https://github.com/owner/repo/issues/123",
    "state": "open"
  },
  "repository": {
    "name": "repo",
    "full_name": "owner/repo",
    "owner": {"login": "owner"},
    "default_branch": "main"
  }
}
```

### SQS Message (Internal)

The Lambda also processes SQS messages for async plan generation and step execution.

**Message Schema:**
```json
{
  "action": "generate_plan",  // or "execute_step"
  "issue_number": 123,
  "issue_title": "Add list-recent-docs handler",
  "issue_description": "Full issue body...",
  "repo_full_name": "owner/repo",
  "branch_name": "123-add-list-recent-docs-handler",
  "current_step": 0,  // 0 for generate_plan
  "total_steps": 0,   // Unknown for generate_plan
  "base_branch": "main",
  "plan_only": false  // If true, skip code generation and create PR with just the plan
}
```

## Message Flow

### 1. Webhook Receipt (Fast Path)
- Validates webhook signature
- Creates git branch: `{issue_number}-{kebab-case-title}`
- Sends "generate_plan" message to SQS FIFO queue
- Returns 200 OK immediately to GitHub

### 2. Plan Generation (Async)
- Queries knowledge base with **repo-prioritized search**:
  - First queries for repo-specific ADRs, patterns, and conventions
  - Then backfills with global/org-wide standards
  - Repo-specific results take precedence (deduplication removes duplicates)
- **Standards summarization with Haiku**:
  - Raw vector search results are passed to ask-claude Lambda
  - Haiku summarizes verbose ADR content into concise standards
  - Keeps cached standards in plans compact (~10-15 lines vs full ADR text)
- Query categories:
  - Handler standards (language-specific patterns)
  - Testing standards (framework-specific)
  - Infrastructure templates (Terraform modules)
  - Language/framework standards
  - Code style preferences
- Generates execution plan with Claude Sonnet
- Breaks work into discrete steps
- Commits plan to branch as `issues/code-gen-plan-{issue_number}.md`
- Sends "execute_step" message for step 1

### 3. Step Execution (Async Loop)
For each step:
- Queries knowledge base for step-specific context
- Generates code files with Claude
- Commits files to branch
- Updates plan with progress
- If more steps: sends message for next step
- If done: creates pull request

### Supported Backends

| Backend | Language/Framework | Use Case |
|---------|-------------------|----------|
| `python-lambda` | Python + AWS Lambda | Serverless Python microservices |
| `java-spring` | Java + Spring Boot | Enterprise Java applications |
| `typescript-express` | TypeScript + Express | Node.js APIs and services |

Each backend provides:
- Language-specific code generation prompts
- Syntax and dependency file validation
- Appropriate test patterns (pytest, JUnit, Jest)
- Code formatters (black, google-java-format, prettier)

When no `.outcomeops.yaml` is present, the system defaults to `python-lambda` backend.

## Repo-Prioritized Knowledge Base Queries

When generating code, the system uses a **repo-prioritized query strategy** to ensure that repository-specific patterns and ADRs take precedence over global org-wide standards.

### How It Works

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    PRIORITIZED KB QUERY FLOW                            │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  Step 1: Query repo-specific documents                                  │
│  ┌──────────────────────────────────────────────────────────────┐      │
│  │  query_knowledge_base(                                        │      │
│  │    queries=["Lambda handler standards"],                      │      │
│  │    repo="spring-petclinic"    ◄── Filter to specific repo    │      │
│  │  )                                                            │      │
│  └──────────────────────────────────────────────────────────────┘      │
│                           │                                             │
│                           ▼                                             │
│  Step 2: Query global/org-wide documents                                │
│  ┌──────────────────────────────────────────────────────────────┐      │
│  │  query_knowledge_base(                                        │      │
│  │    queries=["Lambda handler standards"],                      │      │
│  │    repo=None               ◄── All repos (global)            │      │
│  │  )                                                            │      │
│  └──────────────────────────────────────────────────────────────┘      │
│                           │                                             │
│                           ▼                                             │
│  Step 3: Merge with deduplication                                       │
│  ┌──────────────────────────────────────────────────────────────┐      │
│  │  combined = []                                                │      │
│  │  seen = set()                                                 │      │
│  │                                                               │      │
│  │  # Repo-specific first (takes priority)                       │      │
│  │  for result in repo_results:                                  │      │
│  │      if result[:500] not in seen:                             │      │
│  │          combined.append(result)                              │      │
│  │          seen.add(result[:500])                               │      │
│  │                                                               │      │
│  │  # Global backfill (only non-duplicates)                      │      │
│  │  for result in global_results:                                │      │
│  │      if result[:500] not in seen:                             │      │
│  │          combined.append(result)                              │      │
│  │          seen.add(result[:500])                               │      │
│  └──────────────────────────────────────────────────────────────┘      │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### Why This Matters

Consider a repository like `spring-petclinic` that uses the package structure `org.springframework.samples.petclinic`. Without repo-prioritization:

- Global ADRs might suggest generic patterns like `com.example.project`
- Code generation would use the wrong package naming

With repo-prioritization:

- Repository-specific code maps and ADRs are queried first
- The actual package structure from the repo's code is prioritized
- Generated code follows the existing patterns in the target repository

### Query Categories

For each code generation request, the system queries the following categories using repo-prioritized search:

| Category | Example Queries |
|----------|-----------------|
| Handler Standards | "Lambda handler standards", "Controller patterns" |
| Testing Standards | "pytest patterns", "JUnit test conventions" |
| Infrastructure | "Terraform Lambda module", "Spring Boot configuration" |
| Language Standards | "Python coding conventions", "Java style guidelines" |
| Framework Standards | "Spring Boot patterns", "Express.js middleware" |
| Code Style | "Comment verbosity preferences", "Documentation style" |

**Rules:**
- Lowercase
- Alphanumeric and hyphens only

### Retry Architecture

The code generation system uses a multi-level retry strategy to ensure reliability:

```
┌─────────────────────────────────────────────────────────────────────┐
│                    RETRY FLOW DIAGRAM                                │
├─────────────────────────────────────────────────────────────────────┤
│                                                                      │
│  ┌──────────────┐     ┌──────────────┐     ┌──────────────┐         │
│  │   Step N     │────▶│  Validation  │────▶│   Success    │         │
│  │  Generation  │     │    Check     │     │  Continue    │         │
│  └──────────────┘     └──────────────┘     └──────────────┘         │
│         │                    │                                       │
│         │                    │ Validation Failed                     │
│         │                    ▼                                       │
│         │             ┌──────────────┐                               │
│         │             │  Retry with  │──────▶ Success?               │
│         │             │ Error Feedback│        Continue               │
│         │             └──────────────┘                               │
│         │                    │                                       │
│         │                    │ Still Failed                          │
│         ▼                    ▼                                       │
│  ┌──────────────┐     ┌──────────────┐                               │
│  │  Truncation  │     │ Step Marked  │                               │
│  │  (max_tokens)│     │  as Failed   │                               │
│  └──────────────┘     └──────────────┘                               │
│         │                    │                                       │
│         │                    │                                       │
│         ▼                    ▼                                       │
│  ┌─────────────────────────────────────┐                             │
│  │      SQS Retry (up to 4 times)      │                             │
│  │  - Step error saved to plan file    │                             │
│  │  - Message returns to queue         │                             │
│  │  - On retry: truncation recovery    │                             │
│  └─────────────────────────────────────┘                             │
│                      │                                               │
│                      │ All retries exhausted                         │
│                      ▼                                               │
│  ┌─────────────────────────────────────┐                             │
│  │      Dead Letter Queue (DLQ)        │                             │
│  │  - Creates "salvage" PR with        │                             │
│  │    partial code                     │                             │
│  │  - Comments on GitHub issue         │                             │
│  └─────────────────────────────────────┘                             │
│                                                                      │
└─────────────────────────────────────────────────────────────────────┘
```

### Level 1: Validation Retry (In-Lambda)

When generated code fails syntax validation (e.g., Python syntax errors), the system retries **once** within the same Lambda invocation:

| Attempt | Behavior |
|---------|----------|
| 1st | Normal code generation |
| 2nd | Includes validation error in prompt, asks Claude to fix |

This handles common LLM code generation issues:
- Unterminated string literals
- Mismatched brackets or parentheses
- Invalid indentation
- Missing colons after function/class definitions

**Cost Impact:** Retry uses the same Lambda invocation, so no additional SQS charges.

### Level 2: SQS Retry (Infrastructure)

If the Lambda invocation fails entirely (timeout, crash, unhandled exception), SQS automatically retries:

| Setting | Value | Purpose |
|---------|-------|---------|
| `maxReceiveCount` | 4 | Retry failed messages 4 times |
| `visibilityTimeout` | 900s | Match Lambda timeout (15 min) |

The step's error is persisted to the plan file on each failure, allowing subsequent retries to see what went wrong.

**Cost Impact:** Each SQS retry is a new Lambda invocation (~$0.50-2.00 per attempt with Bedrock).

### Level 3: Truncation Recovery (Smart Retry)

When code generation is truncated (output exceeds `max_tokens=32000`), the step fails with a "truncated" error. On SQS retry, the system detects this and enables **truncation recovery mode**:

```
# Prompt addition when truncation_recovery=True:

⚠️ OUTPUT SIZE LIMIT - GENERATE MINIMAL CODE
Previous attempts to generate this step were truncated due to output size limits.
You MUST generate significantly LESS code this time:

1. If generating tests: Only 1-2 simple test functions, not comprehensive suites
2. If generating handlers: Minimal logic, no verbose error handling
3. If generating modules: Only essential functions mentioned in the step
4. Avoid: Long docstrings, extensive comments, multiple examples
```

This allows large steps to potentially succeed by generating less comprehensive but working code.

**Cost Tracking:** Truncated attempts are logged with wasted cost:
```
[step-exec] Code generation truncated for step 9. Wasted cost: $0.52 (12345 input, 32000 output tokens)
```

### Level 4: Dead Letter Queue (DLQ)

After 4 failed SQS attempts, the message moves to the DLQ. The DLQ handler:

1. **Creates a "salvage" PR** with whatever code was generated before failure
2. **Comments on the GitHub issue** explaining what failed

**DLQ PR Title Format:** `[FAILED] {original issue title}`

**Example Issue Comment:**
```
Code generation failed at step 9 of 12.

A PR has been created with the partial work: https://github.com/owner/repo/pull/42

Please review the generated code and complete the remaining steps manually,
or retry the generation by re-adding the `approved-for-generation` label.
```

### Cost Summary

| Scenario | Typical Cost | What Happens |
|----------|--------------|--------------|
| Success (1st attempt) | $1-3 | Normal generation |
| Validation retry needed | $1.50-4.50 | +50% for retry |
| SQS retry (truncation) | $2-8 | Multiple attempts |
| Max retries + DLQ | $4-12 | All 4 attempts fail, salvage PR created |

| Parameter | Location | Value | Description |
|-----------|----------|-------|-------------|
| `MAX_VALIDATION_RETRIES` | step_executor.py | 1 | In-Lambda validation retries |
| `max_tokens` | step_executor.py | 32000 | Max output tokens per generation |

### Common Errors

**Branch Already Exists:**
- Occurs if issue is re-labeled
- Safe to ignore (existing branch is reused)

**Bedrock AccessDeniedException:**
- Check IAM permissions include inference profile ARNs
- Required: `arn:aws:bedrock:*:*:inference-profile/*`

**Signature Validation Failed:**
- Webhook secret mismatch in SSM
- Check `/{{env}}/{{app}}/github/webhook-secret`

**File Validation Failed:**
- Code generation produced invalid syntax
- Will auto-retry once with error feedback
- If retry fails, step is marked as failed in plan

## EventBridge Notifications

After every successful PR creation the Lambda emits an EventBridge event so downstream automation (run-tests, PR commenters, etc.) can react without polling.

- **Bus:** `${env}-${app}-bus`
- **Source:** `outcomeops.generate-code`
- **Detail Type:** `OutcomeOps.CodeGeneration.Completed`
- **Detail Payload:**
  - `issueNumber`, `issueTitle`, `repoFullName`
  - `branchName`, `baseBranch`, `planFile`
  - `prNumber`, `prUrl`, `commitSha`
  - `environment`, `appName`, `eventVersion`

The `run-tests` Lambda subscribes to this event to clone the branch and run `make test`. Additional consumers can be added via Terraform by pointing new rules at the same bus.

## Performance

### Webhook Response Time
- **Before:** 200+ seconds (synchronous plan generation)
- **After:** <10 seconds (async via SQS)

### Total Generation Time
- **Plan generation:** ~2-3 minutes (3 KB queries + Claude)
- **Per step execution:** ~1-2 minutes (KB query + Claude + commit)
- **5-step feature:** ~10-15 minutes total

### Cost Optimization
- Knowledge base queries reuse vector embeddings
- Claude Sonnet 4.5: ~$3/million input tokens, ~$15/million output tokens
- Typical feature: 50K-100K tokens = $1-3 per generation
